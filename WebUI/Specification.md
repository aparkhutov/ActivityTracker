# Техническая спецификация: ActivityTracker WebUI
Документ описывает архитектуру, API-эндопоинты и логику работы веб-интерфейса дашборда активности.

## 1. Архитектура Web-модуля

* Компонент: Фоновое приложение-сервер (ActivityTrackerWebUI.exe), работающее по протоколу HTTP.
* Порт по умолчанию: 8080 (хост http://localhost:8080).
* Режим работы: Статический файловый сервер + REST API.
* Потоковая модель: Синхронный/асинхронный accept-цикл обработки сетевых сокетов (Winsock ws2_32.lib).

## 2. Логика обработки статики и кэширования

   1. Корневой каталог: Папка ./public, содержащая index.html, style.css, app.js.
   2. Безопасность путей: Сервер проверяет URI на наличие уязвимости Path Traversal (поиск подстроки ..). При обнаружении попытки выхода за пределы папки возвращается 403 Forbidden.
   3. MIME-типы: Сервер парсит расширения запрашиваемых файлов и выставляет корректный заголовок Content-Type (text/html, text/css, application/javascript, application/json) с обязательным указанием кодировки charset=utf-8.
   4. Управление кэшем: Для всех статических ресурсов и JSON-данных отдаются заголовки Cache-Control: no-cache, чтобы браузер всегда отображал актуальную историю активности без перезапуска сервера.

## 3. Спецификация REST API и Форматы Данных## 3.1 Эндопоинт получения данных дашборда

* URL: /data.json
* Метод: GET
* Описание: Возвращает агрегированную информацию об активности пользователя и пользовательские теги. Данные генерируются на основе парсинга файлов логов.
* Формат ответа (JSON):

```json
{
  "data": [
    {
      "index": 1,
      "p": 0,       // Позиция сегмента (время с начала суток в секундах)
      "d": 10,      // Длительность сегмента в секундах
      "status": 1   // 1 - Активен (console/rdp), 0 - Неактивен (off/locked)
    }
  ],
  "total": 1,       // Всего сегментов в массиве
  "totalP": 10,     // Общая временная шкала (последний p + d)
  "totalD": 10,     // Суммарная длительность всех интервалов
  "stats": {
    "active": 1,       // Количество активных сегментов
    "inactive": 0,     // Количество неактивных сегментов
    "activeSum": 10,   // Суммарное время активности (сек)
    "inactiveSum": 0   // Суммарное время бездействия (сек)
  },
  "tags": [            // Пользовательские отметки задач поверх шкалы времени
    {
      "start": 0,
      "duration": 200,
      "name": "Разработка модуля WebUI"
    }
  ]
}
```

### 3.2 Эндопоинт добавления/редактирования тега

* URL: /api/tags
* Метод: POST
* Тело запроса (JSON):

`{ "start": 0, "duration": 120, "name": "Фиксация багов" }`

* Логика сервера: Сервер считывает тело запроса, проверяет валидность регулярными выражениями. Если тег с таким start уже существует — обновляет его duration и name. Если нет — создает новый. Данные сохраняются в tags.csv, после чего обновляется файл data.json.
* Формат успешного ответа:

`{ "success": true, "message": "Tag saved" }`


### 3.3 Эндопоинт удаления тега

* URL: /api/tags
* Метод: DELETE
* Тело запроса (JSON):

`{ "start": 0 }`

* Логика сервера: Ищет в tags.csv запись со значением start. Удаляет строку, перезаписывает файл и обновляет кэш data.json.
* Формат ответа:

`{ "success": true, "message": "Tag deleted" }`


## 4. Логика Фронтенда (app.js)

* Отрисовка таймлайна: График строится на базе Flexbox. Каждому сегменту из data.json присваивается свойство flex-grow пропорционально его длительности d. Зеленый цвет — активность, красный — простой.
* Рендеринг тегов: Слой тегов рендерится над основным графиком активности. Сдвиг влево (margin-left) рассчитывается в процентах как (start / totalP) * 100, а ширина — как (duration / totalP) * 100.
* Интерактивность: Нажатие на любую строку таблицы или на блок тега автоматически заполняет форму редактирования "Add/Edit Tag" данными (start, duration, name).
